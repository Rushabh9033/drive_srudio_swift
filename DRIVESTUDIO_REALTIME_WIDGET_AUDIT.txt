WHY THE WIDGET UPDATES ONLY AFTER OPENING THE APP
-------------------------------------------------
Root cause: the widget timeline's `entry.telemetry` is populated from the App
Group snapshot that the host app writes in `TelemetryService.snapshotAndSave()`.
That function is called from `locationManager(_:didUpdateLocations:)` — which
only fires when Core Location delivers a fix, which only happens while the app
is in the foreground (because background location is misconfigured). So:
  1. User closes app.
  2. iOS suspends the app process.
  3. Core Location stops delivering fixes.
  4. App Group `live_telemetry` value freezes at last foreground speed.
  5. Widget timeline refreshes (if at all) with the frozen value.
  6. User opens app.
  7. Core Location resumes.
  8. didUpdateLocations fires.
  9. snapshotAndSave writes new value.
 10. reloadAllTimelines called.
 11. Widget updates.

Today I added TimelineView(.periodic) which re-reads from UIDevice (battery)
and from UserDefaults (speed) every 1 s inside the widget process. That fixes
battery and re-rendering of cached speed while the widget is on screen. It does
NOT fix the underlying GPS stream being dead while backgrounded.

Two additional contributing causes:
A. `pausesLocationUpdatesAutomatically = false` (line 41) is correct but
   insufficient without `allowsBackgroundLocationUpdates = true`.
B. `UIBackgroundModes` lacks the `location` key, so iOS will not allow
   background location delivery regardless of code intent.

11. FINAL DECISION
================================================================================

  PARTIALLY IMPLEMENTED — CORRECTIVE WORK REQUIRED

Justification
-------------
- The data plumbing inside the host app is correct: real Date(), real UIDevice
  battery, real CLLocation GPS speed, same App Group on both sides, atomic-ish
  write/read.
- The widget timeline + TimelineView self-refresh will keep battery, clock,
  date and the *cached* speed current WHILE the widget process is alive.
- The widget does NOT receive fresh GPS samples while the app is suspended
  because background location is not configured:
    * UIBackgroundModes lacks `location`
    * `allowsBackgroundLocationUpdates` is never set
    * no start/stop lifecycle for an active drive
- There is no Live Activity implementation, so there is no mechanism that can
  show live speed in the Dynamic Island / Lock Screen once the host app is
  suspended. WidgetKit home-screen widgets are not designed for second-by-
  second updates while the host process is suspended.

Root cause of "widget updates only after opening the app"
---------------------------------------------------------
GPS delivery stops when the app suspends (missing background-location config),
so the App Group `live_telemetry` snapshot freezes at the last foreground
value. WidgetKit can only render the value present in the snapshot at the time
of the next timeline refresh. Until the user reopens the app (which re-arms
Core Location), no new fixes arrive, no new snapshot is written, no timeline
refresh reflects newer data. Today's TimelineView edit re-reads the cached
snapshot every 1 s but cannot conjure data that was never written.

What is technically impossible in normal WidgetKit
---------------------------------------------------
A widget extension cannot continuously render at 1 Hz when its process is
suspended. WidgetKit is event-driven: a new Timeline or a `reloadAllTimelines`
call is required to redraw. WidgetKit also caps how often it honors reload
requests, and after long idle the system may stop honoring them entirely.
The TimelineView(.periodic) trick works ONLY while the widget process is
running, which iOS controls. This is why Live Activity exists.

What should be implemented using Live Activity
----------------------------------------------
Any telemetry that must update while the host app is suspended — in
particular, speed during an active drive — should be surfaced through a
Live Activity. The Live Activity gets push-style updates from the host
app (or ActivityKit push tokens) and renders into the Lock Screen and
Dynamic Island independent of whether the host app is suspended.

Live Activity implementation would require:
- New `Widget` declared with `ActivityConfiguration<DriveAttributes>`
- `DriveAttributes: ActivityAttributes` with `ContentState { speed,
  timestamp, distance, ... }`
- `Activity<DriveAttributes>.request(...)` to start
- `await activity.update(.init(state:newState, staleDate:nil))` on each fix
- `NSSupportsLiveActivities = true` in Runner/Info.plist
- Push-to-start token registration for headless start from Core Location

No implementation was performed during this audit.
